## SECTION 1: EMBEDDINGS (Q1–Q15)

**Q1. What is an embedding?**  
A mathematical representation of text as a fixed-size list of numbers where similar meaning = similar numbers. Generated by transformer models trained via contrastive learning.

**Q2. How does cosine similarity work?**  
Measures the angle between two vectors. Formula: (A·B)/(|A|×|B|). Returns 1.0 for identical meaning, 0.0 for unrelated, -1.0 for opposites. We use angle (direction) not distance because sentence length shouldn't affect similarity.

**Q3. Why all-MiniLM-L6-v2 for embeddings?**  
Free, runs locally (no API cost), 384 dimensions (fast), excellent performance on MTEB semantic search benchmark relative to its size.

**Q4. Why cosine over euclidean distance for text embeddings?**  
Curse of dimensionality — in high dimensions all euclidean distances converge. Cosine captures directional meaning regardless of vector magnitude.

**Q5. What happens if you embed with model A and search with model B?**  
Garbage results. The embedding spaces are completely different. Always use the same model for indexing and retrieval.

**Q6. Bi-encoder vs cross-encoder?**  
Bi-encoder: encodes query and doc separately → compare vectors → fast, less accurate. Cross-encoder: encodes (query, doc) together → directly scores relevance → slow, more accurate. Use bi-encoder for retrieval, cross-encoder for reranking.

**Q7. What is embedding drift?**  
When you switch embedding models, old vectors are incompatible. Handle by: versioning embeddings, running background re-indexing, dual retrieval during transition.

**Q8. How do you embed a 50-page document?**  
Don't embed the whole thing at once — models have token limits (~512 tokens). Chunk into smaller pieces first, embed each chunk separately.

**Q9. What is mean pooling in sentence transformers?**  
After the transformer outputs a vector per token, mean pooling averages all token vectors into one sentence-level vector. Alternative: CLS token pooling (use the first [CLS] token's vector).

**Q10. How many tokens can all-MiniLM-L6-v2 handle?**  
512 tokens max. Anything longer is truncated. This is why chunking to ~200-300 tokens is important to leave headroom.

**Q11. What is the MTEB benchmark?**  
Massive Text Embedding Benchmark — standardized evaluation of embedding models across 56 tasks. The best resource for comparing embedding model quality. Used to justify model selection.

**Q12. Why normalize embedding vectors before storing?**  
For cosine similarity, normalized vectors allow dot product to equal cosine similarity — faster computation. Most sentence-transformer models output normalized vectors by default.

**Q13. Can you use one embedding model for multiple languages?**  
Multilingual models like `paraphrase-multilingual-MiniLM-L12-v2` embed 50+ languages into the same space. A query in French can match an English document. Single-language models fail cross-language retrieval.

**Q14. What are dense vs sparse embeddings?**  
Dense: every dimension has a value (what we use — all-MiniLM outputs 384 floats). Sparse: most dimensions are 0, non-zero only for keywords present (BM25 is sparse). Hybrid search uses both.

**Q15. How expensive is embedding 1 million documents?**  
With all-MiniLM on CPU: ~14,000 sentences/second. At avg 5 chunks per doc: 5M chunks / 14,000 = ~6 minutes. On GPU: 20-50x faster. OpenAI text-embedding-3-small: $0.02/1M tokens ≈ $5-10 for 1M docs. Always batch (32-256 at once) for efficiency.

## SECTION 2: VECTOR DATABASES (Q16–Q30)

**Q16. What is a vector database?**  
A database that stores embedding vectors and enables approximate nearest neighbor search. Finds semantically similar items in milliseconds across millions of vectors. Examples: ChromaDB, Pinecone, Weaviate, Qdrant.

**Q17. How does HNSW work?**  
Hierarchical Navigable Small World — builds a multi-layer graph. Top layers: sparse, fast traversal. Bottom layer: dense, all nodes. Query: navigate from top down, refining at each layer. Result: O(log n) search time, ~99% recall.

**Q18. ChromaDB vs Pinecone?**  
ChromaDB: open source, self-hosted, free, good for dev/small scale. Pinecone: managed cloud, paid, scales to billions of vectors, production SLA. Same abstraction, swap with config change.

**Q19. What is metadata filtering in vector DB?**  
Filtering by exact metadata fields alongside vector search. Like "find semantically similar chunks WHERE user_id = 42." Used for multi-tenant isolation.

**Q20. What is a collection in ChromaDB?**  
Analogous to a SQL table. Holds documents, their vectors, and metadata. Can have multiple collections (e.g., one per user or topic).

**Q21. What is pgvector?**  
PostgreSQL extension that adds vector storage and similarity search. Good for smaller scale (< 1M vectors). Avoids running a separate vector DB. We'd use it if already on PostgreSQL and scale doesn't require dedicated vector DB.

**Q22. What are HNSW's key parameters?**  
`M`: connections per node (higher = better recall, more memory). `ef_construction`: candidate list during build (higher = better graph, slower build). `ef` (ef_search): candidate list during query (higher = better recall, slower query).

**Q23. How do you handle deletions in a vector database?**  
Use IDs to delete specific vectors. Challenge: deletions can fragment the HNSW graph. Periodic re-indexing repairs the graph. Soft deletes (metadata flag) avoid frequent hard deletions.

**Q24. What is ANN vs KNN?**  
KNN (K-Nearest Neighbors): exact search, returns perfect top-K. Brute force O(n). ANN (Approximate Nearest Neighbor): returns ~99% accurate top-K. 1000x faster via HNSW/IVF. Production always uses ANN — the 1% accuracy drop is imperceptible to users.

**Q25. How do you ensure isolation between users' documents?**  
Always include user_id in metadata, always filter by it in every query. Defense in depth: also validate at the service layer before querying. Production option: separate Pinecone namespaces per user.

**Q26. How do you choose top-K (number of retrieved chunks)?**  
Balance between: enough context for LLM (higher K) vs noise and context window cost (lower K). Typical: 5-10 chunks. Measure with RAGAS Context Precision — if precision drops as K increases, you're adding noise.

**Q27. What is index warm-up in vector databases?**  
After starting a vector DB, the first few queries are slow as the index loads into memory. Warm up by running a few dummy queries at startup. Important for production — cold starts degrade user experience.

**Q28. What distance metric does Pinecone use?**  
Configurable: cosine, euclidean, or dot product. Choose at index creation — can't change later. For text: always cosine (or dot product if vectors are normalized, which is equivalent).

**Q29. How would you migrate from ChromaDB to Pinecone?**  
Export all vectors + metadata from ChromaDB. Batch upsert to Pinecone (up to 100 vectors per request). Validate: run same queries against both, compare results. Cut over at low traffic time. Keep ChromaDB as backup for 1 week.

**Q30. What is quantization in vector databases?**  
Compressing vectors from float32 to int8 or binary to reduce memory by 4-32x. Reduces accuracy slightly. Pinecone supports scalar quantization natively. Used when storing 100M+ vectors in RAM.

## SECTION 3: RAG PIPELINE (Q31–Q50)

**Q31. What is RAG?**  
Retrieval Augmented Generation. Instead of answering from LLM training data, first retrieve relevant chunks from a knowledge base, then pass them to the LLM as context. Reduces hallucinations, enables private data, enables citation.

**Q32. What are the main failure modes of naive RAG?**  
(1) Poor retrieval — wrong chunks retrieved, LLM gets bad context. (2) Lost in the middle — LLM ignores relevant info buried in long context. (3) Multi-hop failure — question needs info from multiple chunks, single retrieval misses it. (4) Hallucination despite context — LLM ignores context and answers from memory.

**Q33. Explain chunk size vs overlap tradeoff.**  
Smaller chunks: more precise retrieval, lose context. Larger chunks: more context, noisier retrieval, risk truncation. Overlap: prevents losing information at chunk boundaries but increases storage. Typical: 800-1200 chars, 150-200 overlap.

**Q34. What is HyDE?**  
Hypothetical Document Embeddings. Instead of embedding the raw question, ask the LLM to generate a hypothetical answer, then embed that. The hypothetical answer is structurally similar to actual document chunks → higher retrieval similarity. Extra LLM call cost.

**Q35. What is query expansion?**  
Generating multiple versions of a user query to improve retrieval. "What's the refund policy?" → also search for "return policy", "money back", "exchange policy". Retrieve for all versions, deduplicate, pass to LLM.

**Q36. Explain the map-reduce pattern for long documents.**  
If a document is too long for context window: split into sections, send each section to LLM with the question (map step), summarize each response (reduce step), combine summaries into final answer. Enables QA over arbitrarily long documents.

**Q37. What is RAGAS?**  
RAG Assessment framework. Measures: Faithfulness (answer grounded in context?), Answer Relevancy (answer addresses question?), Context Recall (retrieved what was needed?), Context Precision (retrieved only what was needed?).

**Q38. How do you reduce hallucinations in RAG?**  
(1) Include instructions in system prompt: "Only answer using the provided context. If not in context, say so." (2) Citation enforcement: require LLM to quote the source. (3) Faithfulness scoring: post-generate, check if each claim is in retrieved context. (4) Confidence thresholds: if retrieval similarity is below 0.5, refuse to answer.

**Q39. What is self-RAG?**  
The LLM decides when to retrieve. It evaluates its own confidence — if confident (simple factual question), answers directly. If uncertain, triggers retrieval. After retrieval, evaluates if retrieved context is relevant. After generation, scores its own answer for faithfulness. More expensive but more accurate.

**Q40. What is the role of the system prompt in RAG?**  
Sets the LLM's behavior: "You are a helpful assistant. Answer using ONLY the provided context. Always cite the source document and page number. If the answer is not in the context, say 'I don't have that information.'" Well-crafted system prompts are the difference between a RAG that hallucinate and one that doesn't.

**Q41. How do you handle "I don't know" gracefully?**  
When retrieval finds nothing relevant (similarity < threshold): don't pass empty context to LLM. Instead return a structured "no information found" response. Never let LLM guess — it will hallucinate.

**Q42. What is semantic chunking?**  
Split documents at topic boundaries detected by embedding similarity, not by character count. Compare adjacent sentences — when similarity drops sharply, that's a topic boundary → split there. More expensive but produces more coherent chunks.

**Q43. What is the context window in an LLM?**  
Maximum tokens the LLM can process at once. GPT-4o: 128K. Llama 3.3-70B on Groq: 128K. The entire conversation (system prompt + retrieved context + conversation history + question) must fit within this limit.

**Q44. How do you handle multi-turn conversations in RAG?**  
Challenge: "What about the refund policy?" — the pronoun "it" has no meaning without conversation history. Solutions: (1) Condense query: ask LLM to rewrite the latest question incorporating conversation history into a standalone question. (2) Conversation-aware retrieval: include recent turns in the query embedding.

**Q45. What is document re-ranking?**  
After initial retrieval (bi-encoder), run a cross-encoder on each (query, chunk) pair to get a precise relevance score. Sort by cross-encoder score. Return top-K. Improves answer quality significantly at the cost of extra compute.

**Q46. How do you handle tables and structured data in RAG?**  
Plain text chunking destroys table structure. Solutions: (1) Convert tables to natural language ("Row 1: Product=A, Price=$10, Stock=50"). (2) Use specialized table-aware embeddings. (3) For structured queries, use SQL generation over a database rather than RAG.

**Q47. What is citation in RAG and how is it implemented?**  
Citation = telling the user which document/page the answer came from. Implementation: store document_id, page_number, chunk_index as metadata. When retrieving, pass this metadata alongside the text. Prompt the LLM to reference source IDs. Return both the answer and the source metadata to the frontend.

**Q48. What is faithfulness scoring?**  
Post-generation check: does every factual claim in the answer have support in the retrieved context? Use an LLM or NLI model to check each sentence of the answer against the context. Faithfulness < 0.7 → flag as potentially hallucinated.

**Q49. How do you handle documents in multiple languages?**  
(1) Multilingual embeddings (embed all docs in same space). (2) Language detection on query, search in matching language docs. (3) Machine translation: translate all docs to English at index time. (4) Cross-lingual retrieval: multilingual model handles query-doc matching across languages.

**Q50. RAG vs Fine-tuning — give a complete answer.**  
RAG: retrieval from external storage, no model modification, always up to date, citations possible, 0 training cost. Fine-tuning: knowledge baked into weights, no retrieval overhead, lower latency, expensive to update. Choose RAG when: private/changing data, need citations, can't afford retraining. Choose fine-tuning when: specific behavior/style needed, stable domain knowledge, strict latency requirements. Best: combine — fine-tune for style, RAG for knowledge.

## "TELL ME ABOUT YOUR PROJECT" — 3 VERSIONS

### 30 seconds (elevator pitch)
"I built Nexus AI — an enterprise platform where you upload any documents and ask questions in plain English. It uses RAG: your documents are indexed as semantic embeddings in a vector database, and when you ask a question, the system retrieves the most relevant parts and generates an accurate, cited answer. Production stack: FastAPI, LangGraph agents, ChromaDB/Pinecone, Next.js."

### 2 minutes (technical interview)
"Nexus AI is a production-grade multi-agent RAG platform. I built the complete pipeline from scratch: documents are loaded using PyPDF and UnstructuredLoader, chunked with RecursiveCharacterTextSplitter using 1000-char chunks and 200-char overlap, embedded with all-MiniLM-L6-v2 for local dev or text-embedding-3-small for production, and stored in ChromaDB or Pinecone. On query, we use hybrid retrieval — semantic search plus BM25 — then rerank with a cross-encoder, and pass the top-5 chunks to Llama 3.3 via Groq for grounded answer generation. The multi-agent layer uses LangGraph: a Planner agent decomposes complex questions, parallel Research agents retrieve from the knowledge base, and a Synthesis agent combines results with citations. The system is deployed with FastAPI backend, Next.js frontend with streaming WebSocket responses, Celery for async document processing, Redis for caching and rate limiting, Docker for containerization, and monitored with Langfuse for LLM tracing."
